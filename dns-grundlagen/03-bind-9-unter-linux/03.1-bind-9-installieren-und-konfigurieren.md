## Lernziele

Nach dieser Übung kannst du

- BIND 9 unter Debian/Ubuntu prüfen bzw. installieren und den Dienst über `systemd` verwalten,
- die Konfigurationsstruktur unter `/etc/bind/` (`named.conf`, `named.conf.options`, `named.conf.local`, `named.conf.default-zones`) lesen und bearbeiten,
- eine Zugriffskontrollliste (`acl`), die Lauschschnittstellen (`listen-on`, `listen-on-v6`) und die Zugriffsrechte (`allow-query`, `allow-recursion`) konfigurieren,
- Konfigurationsdateien mit `named-checkconf` prüfen, bevor du sie lädst,
- mit `rndc` den laufenden Server steuern und das Protokoll auswerten,
- den Unterschied zwischen Neustart und Neuladen erklären.

- Der Dienst `named` ist am Ende von Modul 01 deaktiviert worden; er wird hier gestartet.
- Zugriff als `root` oder per `sudo`.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **named** | Der BIND-Daemon (Name des Programms). |
| **named.conf** | Hauptdatei; bindet unter Debian/Ubuntu die anderen Dateien per `include` ein. |
| **named.conf.options** | Globale Einstellungen (`options { … };`). |
| **named.conf.local** | Eigene Zonen, hier ergänzt du Zonen. |
| **named.conf.default-zones** | Standardzonen: Wurzel (Hint), `localhost`, Rückwärtszonen für Loopback u. a. |
| **acl** | Benannte Adressliste, die an mehreren Stellen benutzt werden kann. |
| **listen-on / listen-on-v6** | IPv4- bzw. IPv6-Adressen, auf denen `named` Anfragen annimmt. |
| **allow-query / allow-recursion** | Wer fragen darf / für wen der Server rekursiv auflöst. |
| **rndc** | Fernsteuerung des laufenden `named` über Port 953, authentifiziert mit einem gemeinsamen Schlüssel (`rndc.key`). |
| **AppArmor-Profil** | Zugriffsbeschränkung für den Prozess (Ubuntu: `/etc/apparmor.d/usr.sbin.named`). |

## Aufgabe

Jeder Schritt steht auf zwei Wegen, wo es zwei gibt: grafisch gibt es unter Linux (Server ohne Oberfläche) selten einen Weg. Wo ein Weg fehlt, steht das dabei. Alle Befehle laufen mit `sudo` oder als `root`.

### Teil 1: BIND prüfen und starten

*(Lerneinheit 3.1, Praxisaufgabe 1)*

**1. Pakete und Version prüfen**

```bash
dpkg -l bind9 bind9utils bind9-dnsutils | grep '^ii'
named -V | head -3
```

Erwartet (*Testumgebung, Versionsnummern sinngemäß*): drei Zeilen mit Status `ii`; `named -V` meldet `BIND 9.18.…` (Ubuntu 24.04) bzw. `9.18.…` (Debian 12, *nicht bestätigt*).

Falls ein Paket fehlt (nur mit Netz oder ISO möglich):

```bash
sudo apt update
sudo apt install -y bind9 bind9utils bind9-dnsutils bind9-doc
```

**2. Systembenutzer und Sicherheitskontext ansehen**

```bash
id bind
ls -l /etc/bind
ls -ld /var/cache/bind /var/lib/bind
ls -l /etc/apparmor.d/usr.sbin.named
```

Notiere: Wem gehört `/var/cache/bind`? Welche Rechte hat die Gruppe `bind`? Das AppArmor-Profil legt (im Testsystem gelesen) fest: `/etc/bind/**` nur lesbar, `/var/lib/bind/**` les- und schreibbar (für dynamisch aktualisierte Zonen und Journal-Dateien) und `/var/cache/bind/**` les- und schreibbar (für Daten von sekundären Zonen und Stub-Zonen). Das merkst du dir für Modul 06 und Modul 08.

**3. Dienst starten und prüfen**

Der Dienst heißt je nach Version `named` oder `bind9`; der jeweils andere Name ist ein Alias (*nicht bestätigt* für beide Versionen).

```bash
sudo systemctl enable --now named || sudo systemctl enable --now bind9
systemctl status named --no-pager || systemctl status bind9 --no-pager
```

Erwartet (*sinngemäß, nicht bestätigt*): `active (running)`.

**4. Prüfen, worauf `named` lauscht**

```bash
sudo ss -tulnp | grep named
```

In der Testumgebung mit der Konfiguration aus Teil 3 war das Ergebnis (gekürzt auf Adresse und Port):

```text
udp   127.0.0.1:53
udp   192.168.50.11:53
tcp   127.0.0.1:53
tcp   192.168.50.11:53
tcp   127.0.0.1:953
```

Port 53 ist die DNS-Abfrage (UDP und TCP), Port 953 die Verwaltung mit `rndc` (nur Loopback). Vor Teil 3 (Standardkonfiguration) lauscht `named` auf allen Adressen des Servers; notiere das und vergleiche nach Teil 3.

### Teil 2: Die Konfigurationsstruktur lesen

*(Lerneinheit 3.2)*

**1. Die Dateien lesen**

```bash
cat /etc/bind/named.conf
cat /etc/bind/named.conf.options
cat /etc/bind/named.conf.local
cat /etc/bind/named.conf.default-zones
```

`named.conf` enthält im Wesentlichen drei `include`-Zeilen. Notiere, welche Datei wofür zuständig ist und welche Zonen in `named.conf.default-zones` stehen.

**2. Die wirksame Gesamtkonfiguration ausgeben**

```bash
named-checkconf -p | less
```

`named-checkconf -p` gibt die fertig zusammengesetzte Konfiguration (mit allen `include`-Dateien) normalisiert aus. Suche darin die `options`- und die `acl`-Blöcke und die Zone `localhost`.

**3. Die Syntaxregeln üben**

BIND-Konfigurationen sind Anweisungen aus Name, Wert und Block, jede Anweisung endet mit `;`, jeder Block wird mit `{ … };` geschlossen. Kommentare: `//`, `#` oder `/* … */`. Lege eine Kopie an und füge einen Kommentar jeder Art ein:

```bash
sudo cp /etc/bind/named.conf.options /root/named.conf.options.orig
sudoedit /etc/bind/named.conf.options
```

```text
// Kommentar im C++-Stil
# Kommentar im Shell-Stil
/* Kommentar über
   mehrere Zeilen */
```

Dann `named-checkconf` ausführen: Es darf nichts ausgeben (Stille ist Erfolg).

### Teil 3: ACL, Lauschadressen und Zugriffsrechte

*(Lerneinheit 3.3, Praxisaufgabe 2)*

**1. Die Optionsdatei anpassen**

Ersetze den Inhalt von `/etc/bind/named.conf.options` durch die Datei `03.1-named.conf.options` dieser Übung (oder ändere die Abschnitte von Hand):

```text
acl "lab-nets" {
    127.0.0.0/8;
    192.168.50.0/24;
    ::1/128;
    fd00:50::/64;
};

options {
    directory "/var/cache/bind";

    listen-on    { 127.0.0.1; 192.168.50.11; };
    listen-on-v6 { ::1; fd00:50::11; };

    allow-query { lab-nets; };
    allow-recursion { lab-nets; };

    dnssec-validation auto;
};
```

Die `acl` steht **außerhalb** des `options`-Blocks, aus Gründen der Lesbarkeit davor. (Die Reihenfolge ist für `named-checkconf` nebensächlich: Eine ACL, die erst nach ihrer Verwendung definiert wird, wird akzeptiert, so gemessen. Eine ACL, die nirgends definiert ist, nicht: `undefined ACL 'lab-nets'`.) `dnssec-validation auto` ist Standard der Distribution; DNSSEC ist nicht Thema dieser Reihe.

**2. Prüfen und laden**

```bash
sudo named-checkconf
sudo rndc reload
```

Erwartet (so gemessen): `named-checkconf` gibt nichts aus, `rndc reload` meldet `server reload successful`. **Hinweis:** Die Änderung der **Lauschadressen** wird zuverlässig erst nach einem Neustart oder mit `rndc reconfig` übernommen; bei Zweifeln `sudo systemctl restart named` (bzw. `bind9`).

**3. Wirkung prüfen**

```bash
sudo ss -tulnp | grep named
dig @192.168.50.11 localhost A +short
```

Erwartet (so gemessen): `127.0.0.1`. Nach dem Aufruf mit `ss` darf kein `0.0.0.0:53` oder `[::]:53` mehr auftauchen.

Von CLI-TEST-01 (Windows):

```powershell
Resolve-DnsName -Name localhost -Server 192.168.50.11
```

Erwartet (*nicht bestätigt*): eine Antwort mit `127.0.0.1`. `localhost` wird von der Standardzone `localhost` beantwortet.

> [!NOTE]
> Die Datei `/etc/bind/named.conf.options` im Labor ist **keine** Konfiguration für ein Produktivsystem. `allow-recursion` und `allow-query` sind hier so eng gesetzt, dass der Server nicht zum offenen Resolver wird. Das ist der wichtigste Grund, sie zu setzen.

**4. Zugriffsschutz sichtbar machen**

Schränke vorübergehend `allow-query` ein, lade neu und frage von einer Adresse außerhalb:

```bash
sudo sed -i 's/allow-query { lab-nets; };/allow-query { 127.0.0.1; };/' /etc/bind/named.conf.options
sudo named-checkconf && sudo rndc reload
dig @192.168.50.11 localhost A | grep -E 'status|EDE'
dig @127.0.0.1 localhost A | grep status
```

Erwartet (so gemessen): Die Abfrage an `192.168.50.11` wird mit `status: REFUSED` und `EDE: 18 (Prohibited)` beantwortet, die an `127.0.0.1` mit `NOERROR`. (Die Abfrage kommt von der Adresse `192.168.50.11` selbst, die in `lab-nets`, aber nicht in `{ 127.0.0.1; }` steht.)

Danach **zurücksetzen**:

```bash
sudo sed -i 's/allow-query { 127.0.0.1; };/allow-query { lab-nets; };/' /etc/bind/named.conf.options
sudo named-checkconf && sudo rndc reload
```

### Teil 4: Syntaxprüfung, rndc und Protokoll

*(Lerneinheit 3.4, Praxisaufgabe 3)*

**1. Absichtlich einen Fehler einbauen**

Entferne in der `listen-on`-Zeile das Semikolon nach der letzten Adresse:

```text
listen-on    { 127.0.0.1; 192.168.50.11 };
```

```bash
sudo named-checkconf
```

Erwartet (so gemessen, bei der Datei dieser Übung ist die `listen-on`-Zeile die 15.):

```text
/etc/bind/named.conf.options:15: missing ';' before '}'
```

Merke: Die Zeilenangabe zeigt, **wo der Parser den Fehler bemerkt**; die Ursache liegt oft in der Zeile davor oder in derselben Zeile.

**2. Fehler beheben und neu prüfen**

Semikolon wieder setzen, `sudo named-checkconf` (stumm), dann laden:

```bash
sudo rndc reload
```

**3. Zustand mit rndc**

```bash
sudo rndc status
sudo rndc reconfig
```

`rndc status` zeigt unter anderem Version, Startzeit, Zeitpunkt der letzten Konfiguration, Konfigurationsdatei, Anzahl CPUs, Worker-Threads, Zonenzahl und Debug-Stufe (so gemessen). `rndc reconfig` lädt die Konfiguration und **neue** Zonen, ohne bereits geladene Zonen neu einzulesen; es meldet bei Erfolg nichts.

**4. Protokoll lesen**

```bash
sudo journalctl -u named -u bind9 -n 20 --no-pager
```

Erwartet (*Dienstprotokoll unter systemd, nicht bestätigt*): Meldungen des Dienstes. In der Testumgebung (Vordergrundbetrieb, nicht `systemd`) zeigte das Protokoll nach `rndc reload` und `rndc reconfig`:

```text
received control channel command 'reload'
reloading configuration succeeded
reloading zones succeeded
received control channel command 'reconfig'
reloading configuration succeeded
```

Suche die entsprechenden Zeilen in deinem Protokoll.

**5. Neustart und Neuladen vergleichen**

```bash
# Terminal 1: Dauerabfrage
while true; do dig @192.168.50.11 localhost A +short +time=1 +tries=1 || echo FEHLER; sleep 0.2; done
```

```bash
# Terminal 2
sudo rndc reload
sudo systemctl restart named
```

Beobachte in Terminal 1, ob Fehlermeldungen auftreten. Notiere Unterschiede (*Beobachtung nicht bestätigt*, da nicht unter `systemd` getestet; ein sehr kurzer Ausfall beim Neustart ist zu erwarten).

**6. Gesamtprüfung**

```bash
bash 03.1-bind-pruefen.sh
```

Das Skript prüft Pakete, Benutzer, Dienst, Syntax, ACL, Lauschadressen, Ports 53 und 953, `rndc` und eine Testabfrage. Alle Zeilen sollen mit `OK` beginnen.

## Hintergrund

### Warum mehrere Dateien?

Debian/Ubuntu teilen die Konfiguration, damit Paketupdates die globalen Optionen und die Standardzonen ersetzen können, ohne deine eigenen Zonen in `named.conf.local` anzutasten. Du änderst `named.conf.options` (Optionen) und `named.conf.local` (Zonen); `named.conf.default-zones` lässt du in Ruhe.

### rndc und der Schlüssel

`rndc` verbindet sich standardmäßig mit `127.0.0.1` Port 953 und weist sich mit dem Schlüssel aus `/etc/bind/rndc.key` aus. Ohne passenden Schlüssel lehnt `named` die Verbindung ab. Unter Debian/Ubuntu ist der Schlüssel dem Benutzer/der Gruppe `bind` zugeordnet; `sudo` genügt.

### ACLs und Zugriffsrechte

Ohne `allow-query` beantwortet der Server fast jede Anfrage von überall; ohne `allow-recursion` löst er für fast jeden rekursiv auf (die Distributionen setzen sichere Standardwerte, aber verlasse dich nicht darauf). Eine `acl` bündelt die zulässigen Netze an einer Stelle.

### Neustart und Neuladen

`systemctl restart named` beendet den Prozess und startet ihn neu: Zwischenspeicher und Verbindungen sind weg, es gibt einen kurzen Ausfall. `rndc reload` (und `reconfig`) lässt den Prozess laufen und liest nur Konfiguration und Zonen neu; Antworten laufen weiter.

### Rechte und AppArmor

`named` läuft als Benutzer `bind`. Dateien, die er schreiben muss (Journal, Daten von Sekundärzonen, dynamische Zonen), gehören nach `/var/lib/bind` bzw. `/var/cache/bind`. Liegt eine schreibende Zonendatei woanders, scheitert das Schreiben an den Dateirechten oder (Ubuntu) am AppArmor-Profil. Der Server startet dann oft trotzdem; das Problem zeigt sich im Protokoll und beim nächsten Schreibvorgang.

## Hinweise

- **Vor jeder Änderung** eine Kopie der Datei anlegen oder einen Snapshot machen.
- `named-checkconf` prüft die **Syntax**, nicht die Logik. Ein Tippfehler in einer Adresse ist gültig und trotzdem falsch.
- Auf Ubuntu reicht oft `sudo systemctl reload named`; unter Debian kann `reload` je nach Einheit nicht definiert sein (*nicht bestätigt*). `rndc reload` ist unabhängig davon.
- IPv6: Die Adresse `fd00:50::11` muss auf der Schnittstelle liegen, sonst kann `named` nicht darauf binden (Meldung im Protokoll, *nicht bestätigt*). Die Testumgebung hatte keine IPv6-Unterstützung; die Zeile wurde mit `named-checkconf` auf Syntax geprüft, die Bindung nicht.
- Die Zonen aus `named.conf.default-zones` (Loopback, Wurzel-Hint) sind nötig; entferne sie nicht.

**Kontrollfragen**

1. Warum teilt Debian/Ubuntu die BIND-Konfiguration in mehrere Dateien wie `named.conf.options` und `named.conf.local` auf, statt alles in `named.conf` zu schreiben?
2. Welche Aufgabe erfüllt `rndc`, über welchen TCP-Port spricht es standardmäßig mit `named`, und wie wird die Verbindung abgesichert?
3. Welches Risiko besteht, wenn ein neues Verzeichnis für Zonendateien nicht dem Benutzer/der Gruppe `bind` gehört oder im AppArmor-Profil nicht freigegeben ist?
4. Worin liegt der Unterschied zwischen `systemctl restart named` und `rndc reload` im laufenden Betrieb?
5. Was bedeutet `REFUSED` mit `EDE: 18 (Prohibited)`, und was muss man ändern, damit die Anfrage beantwortet wird?
6. Was meldet `named-checkconf`, wenn `allow-query` eine ACL nennt, die nirgends definiert ist? Spielt die Reihenfolge von `acl` und `options` eine Rolle?

### Antworten auf die Kontrollfragen

1. Damit Paketupdates Teile ersetzen können, ohne eigene Zonen zu berühren, und damit jede Datei eine klare Aufgabe hat: Optionen, eigene Zonen, Standardzonen.
2. Fernsteuerung des laufenden `named` (Neuladen, Status, Zwischenspeicher leeren u. a.). Standardport TCP 953 auf Loopback; Authentifizierung über einen gemeinsamen Schlüssel (`rndc.key`, HMAC).
3. `named` kann die Datei nicht schreiben oder (wenn nur lesbar) nicht ändern: Zonenübertragungen, dynamische Updates und Journal scheitern. Ubuntu blockiert zusätzlich über AppArmor; die Ablehnung steht im Systemprotokoll (`DENIED` in den Kernel-Meldungen bzw. im Journal, *nicht bestätigt*).
4. `restart`: Prozess wird beendet und gestartet; kurzer Ausfall, Zwischenspeicher weg. `reload`: Prozess läuft weiter, Konfiguration und Zonen werden neu gelesen, kein Ausfall.
5. Die Anfrage kam von einer Adresse, die `allow-query` nicht zulässt; der Server verweigert die Antwort. Ändern: Adresse bzw. Netz in `allow-query` (oder die dort genutzte `acl`) aufnehmen.
6. Bei einer nirgends definierten ACL meldet `named-checkconf` `undefined ACL 'lab-nets'` (mit Dateiname und Zeile) und endet mit Fehlercode. Die Reihenfolge von `acl` und `options` ist egal: Eine erst nach `options` definierte ACL wurde in der Testumgebung ohne Fehler akzeptiert (so gemessen).
