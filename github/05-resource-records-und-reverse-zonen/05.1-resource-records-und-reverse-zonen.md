## Lernziele

Nach dieser Übung kannst du

- Aufbau und Felder eines Resource Records (Name, TTL, Klasse, Typ, RDATA) erklären,
- A, AAAA, CNAME, MX, TXT, SRV und PTR einsetzen und ihre Grenzen nennen (z. B. kein CNAME am Zonenursprung),
- Reverse-Zonennamen für IPv4 (`in-addr.arpa`) und IPv6 (`ip6.arpa`, Nibble-Format) berechnen,
- alle genannten Eintragstypen unter Windows (GUI und PowerShell) und in BIND-Zonendateien anlegen,
- `$TTL`, `$ORIGIN`, `@` und den abschließenden Punkt in Zonendateien richtig lesen und schreiben,
- Fehler in Zonendateien an den Meldungen von `named-checkzone` und an der `dig`-Ausgabe erkennen.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Resource Record (RR)** | Ein Datensatz im DNS: `Name TTL Klasse Typ RDATA`. |
| **Klasse** | In der Praxis immer `IN` (Internet). |
| **RDATA** | Die typabhängigen Daten (bei A: eine IPv4-Adresse). |
| **RRset** | Alle Einträge desselben Namens und Typs. |
| **Zonenursprung (Apex)** | Der Name der Zone selbst, in Zonendateien `@`. |
| **FQDN** | Vollständiger Name; in Zonendateien mit abschließendem Punkt. |
| **Nibble** | Eine Hexadezimalziffer (4 Bit). Die IPv6-Reverse-Auflösung arbeitet nibbleweise. |
| **PTR** | Zeigt von einer Adresse (im Reverse-Baum) auf einen Namen. |

### Teil 1: Aufbau eines Resource Records

*(Lerneinheit 5.1)*

**1. Eine Zonenzeile zerlegen**

Lies diese Zeile aus der Zonendatei von `branch.example.org`:

```text
www       3600  IN  CNAME  web
```

Ordne zu: Welches Feld ist der Name, die TTL, die Klasse, der Typ, die RDATA? Warum steht hinter `web` kein Punkt, und wie lautet der vollständige Name des Ziels?

**2. Regeln für CNAME**

Entscheide für jede Zeile, ob sie in einer Zone erlaubt ist, und begründe in einem Satz (RFC 1034, RFC 2181):

| Zeile (Zone `branch.example.org`) | erlaubt? | Begründung |
|---|---|---|
| `www IN CNAME web` | | |
| `@ IN CNAME web` | | |
| `www IN CNAME web` und zusätzlich `www IN A 192.168.50.99` | | |
| `@ IN MX 10 www.branch.example.org.` (www ist ein CNAME) | | |

**3. Antworten lesen**

Frage `www.branch.example.org` einmal nach `CNAME` und einmal nach `A`:

Erwartet (so gemessen, Zonendatei aus Teil 4 geladen):

und bei `A`:

```text
www.branch.example.org.	3600	IN	CNAME	web.branch.example.org.
web.branch.example.org.	3600	IN	A	192.168.50.40
```

Erkläre, warum die zweite Antwort zwei Zeilen enthält.

### Teil 2: Forward-Einträge auf SRV-WIN-DNS

*(Lerneinheiten 5.1 und 5.2, Praxisaufgabe 1)*

Ziel: In der Zone `corp.example.com` stehen am Ende diese Einträge:

| Name | Typ | Wert |
|---|---|---|

| `files` | A / AAAA | `192.168.50.20` / `fd00:50::20` |

**1. Einträge anlegen**

- **GUI:** DNS-Manager → *Forward-Lookupzonen* → `corp.example.com` → Rechtsklick → *Neuer Host (A oder AAAA)…*, *Neuer Alias (CNAME)…*, *Neuer Mailaustauscher (MX)…* und *Weitere neue Einträge…* (für TXT und SRV). Beim Host-Eintrag den Haken *Zugeordneten Zeigereintrag (PTR) erstellen* **nicht** setzen; die PTR-Einträge legst du in Teil 3 selbst an. Die Bezeichnungen der deutschen Oberfläche sind *nicht bestätigt*.
- **PowerShell:** Ein Eintrag je Typ, zum Beispiel:

```powershell
Add-DnsServerResourceRecord -ZoneName corp.example.com -A    -Name files    -IPv4Address 192.168.50.20
Add-DnsServerResourceRecord -ZoneName corp.example.com -AAAA -Name files    -IPv6Address fd00:50::20
Add-DnsServerResourceRecord -ZoneName corp.example.com -CName -Name intranet -HostNameAlias files.corp.example.com
Add-DnsServerResourceRecord -ZoneName corp.example.com -MX -Name . -MailExchange mail.corp.example.com -Preference 10
Add-DnsServerResourceRecord -ZoneName corp.example.com -Srv -Name _sip._tcp -DomainName voip.corp.example.com -Priority 10 -Weight 100 -Port 5060
```

```powershell

.\05.1-corp-records-anlegen.ps1
```

  Der Punkt als Name beim MX-Eintrag steht für den Zonenursprung (so im Beispiel in Microsoft Learn). Für den TXT-Eintrag am Zonenursprung verwendet das Skript `@`; das ist **nicht bestätigt**. Meldet Windows einen Fehler, rufe das Skript mit `-ApexName .` auf.

**2. Prüfen**

### Teil 3: Reverse-Zonen berechnen und anlegen

*(Lerneinheit 5.3, Praxisaufgabe 2)*

**1. Rechnen**

IPv4: Die Adresse wird Oktett für Oktett umgekehrt, dahinter steht `in-addr.arpa`. Fülle aus:

| Adresse | Name des PTR-Eintrags (vollständig) | Zone (`/24`) | Name innerhalb der Zone |
|---|---|---|---|
| `192.168.50.10` | | | |
| `192.168.50.25` | | | |
| `192.168.50.100` | | | |

| Adresse | ausgeschrieben | Name des PTR-Eintrags (vollständig) |
|---|---|---|
| `fd00:50::10` | | |

b) **CNAME am Zonenursprung:** zusätzlich `@ IN CNAME web`

```text

zone branch.example.org/IN: loading from master file /tmp/c/b failed: CNAME and other data
zone branch.example.org/IN: not loaded due to errors.
```

(so gemessen, Dateipfad und Zeilennummer hängen von deiner Datei ab). Am Zonenursprung stehen immer SOA und NS.

c) **MX-Ziel ohne Punkt:** `@ IN MX 10 linserver.branch.example.org`

```text
zone branch.example.org/IN: branch.example.org/MX 'linserver.branch.example.org.branch.example.org' has no address records (A or AAAA)
zone branch.example.org/IN: loaded serial 2026111101
OK
```

(so gemessen). Diesmal bemerkt `named-checkzone` das Problem, weil für MX geprüft wird, ob das Ziel eine Adresse hat, doch es ist nur eine **Warnung** (Rückgabewert 0).

d) **MX auf einen Alias:** `@ IN MX 10 www.branch.example.org.`

```text

zone branch.example.org/IN: loaded serial 2026111101
OK
```

(so gemessen). Auch das ist nur eine Warnung. Ein MX-Ziel darf kein CNAME sein (RFC 2181).

e) **TXT ohne Anführungszeichen:** `@ IN TXT v=spf1 mx -all`

Die Datei lädt ohne Fehler. Die Antwort lautet:

```text
branch.example.org.	3600	IN	TXT	"v=spf1" "mx" "-all"
```

(so gemessen). Aus einem Text wurden drei getrennte Zeichenketten. Manche Auswertungen (zum Beispiel SPF) fügen sie wieder zusammen, andere nicht; setze deshalb immer Anführungszeichen.

f) **Ungültige IPv6-Adresse:** `web IN AAAA fd00:50::40::1`

```text
dns_rdata_fromtext: /tmp/c/g:19: near 'fd00:50::40::1': bad IPv6 address
zone branch.example.org/IN: loading from master file /tmp/c/g failed: bad IPv6 address
zone branch.example.org/IN: not loaded due to errors.
```

(so gemessen).

## Hintergrund

### Aufbau eines Resource Records

Ein Eintrag besteht aus Name, TTL, Klasse, Typ und typabhängigen Daten (RFC 1035). In Zonendateien dürfen TTL und Klasse fehlen (Standardwerte aus `$TTL` und `IN`), und der Name darf fehlen (dann gilt der vorherige).

### Die Typen im Überblick

| Typ | Zweck | Besonderheit |
|---|---|---|
| A | Name → IPv4 | Mehrere A-Einträge am selben Namen sind erlaubt. |
| AAAA | Name → IPv6 | RFC 3596. |
| CNAME | Alias auf einen anderen Namen | Der Name darf sonst nichts haben; nicht am Zonenursprung (RFC 1034, RFC 2181). |
| MX | Mailserver der Domain | Kleinere Präferenz zuerst; Ziel muss ein Name mit A/AAAA sein, kein CNAME. |
| TXT | Freier Text | SPF, DKIM, DMARC, Domain-Bestätigungen. |
| SRV | Dienstort | `_dienst._protokoll.name TTL IN SRV Priorität Gewichtung Port Ziel` (RFC 2782). |
| PTR | Adresse → Name | Steht im Reverse-Baum. |

### Reverse-Auflösung

Der Reverse-Baum folgt dem Aufbau der Adresse: bei IPv4 Oktett für Oktett, bei IPv6 Nibble für Nibble (RFC 3596), jeweils in umgekehrter Reihenfolge, weil die Delegation im DNS von rechts nach links verläuft. Ein `/24` entspricht einer Zone (`50.168.192.in-addr.arpa`), ein `/64` einer Zone mit 16 Nibbles.

### Der abschließende Punkt

In Zonendateien (BIND wie Windows) gilt: Namen **ohne** Punkt am Ende sind relativ und bekommen den Ursprung angehängt; Namen **mit** Punkt sind vollständig. Der häufigste Fehler in der Praxis ist ein vollständiger Name ohne Punkt. In den PowerShell-Cmdlets von Windows gibst du Namen dagegen als gewöhnliche FQDN an (die Beispiele in Microsoft Learn schreiben sie ohne Punkt).

## Hinweise

- Das Verhalten bei Namen **ohne** Punkt in Windows-Cmdlets (zum Beispiel `-PtrDomainName`) ist nicht dasselbe wie in einer BIND-Zonendatei. Prüfe das Ergebnis immer mit `Resolve-DnsName`.
- `named-checkzone` prüft Syntax und einige Plausibilitäten; ein falsch gemeinter, aber gültiger Name bleibt unbemerkt (siehe Teil 5, a).
- Nach jeder Änderung an einer BIND-Zonendatei die Seriennummer erhöhen (Modul 04, Teil 4) und `rndc reload` ausführen.
- Die Einträge und Zonen bleiben für die folgenden Module bestehen.

**Kontrollfragen**

1. Warum darf am Zone Apex (also für den Domänennamen selbst, z. B. `corp.example.com`) laut DNS-Spezifikation (RFC 1034 / RFC 2181) kein `CNAME`-Record angelegt werden?
2. Ein Unternehmen betreibt zwei Mailserver mit `MX`-Einträgen der Präferenzwerte `10` (`mail1`) und `20` (`mail2`). In welcher Reihenfolge versucht ein externer Mailserver die Zustellung, und wie verhält es sich, wenn beide `MX`-Einträge denselben Präferenzwert `10` besitzen?
3. Wie lautet der exakte Name des `PTR`-Eintrags (inklusive Zonensuffix) für die IPv4-Adresse `192.168.50.25` und wie wird das Nibble-Format für IPv6-Reverse-Zonen gebildet?
4. Was passiert in einer BIND-9-Zonendatei für die Zone `branch.example.org`, wenn Sie als Ziel eines `CNAME`-Eintrags `web.branch.example.org` (ohne abschließenden Punkt am Ende) eintragen?
5. Warum meldet `named-checkzone` in Teil 5, a) keinen Fehler, obwohl der Eintrag nicht funktioniert?

### Teil 1

1. Name `www`, TTL `3600`, Klasse `IN`, Typ `CNAME`, RDATA `web`. Der Name steht ohne Punkt und ist deshalb relativ; sein Ziel lautet `web.branch.example.org.`.

| Zeile | erlaubt? | Begründung |
|---|---|---|
| `www IN CNAME web` | ja | Alias ohne weitere Daten am Namen. |
| `@ IN CNAME web` | nein | Am Zonenursprung stehen SOA und NS; ein CNAME verträgt keine anderen Daten. |
| `www` mit CNAME und A | nein | CNAME schließt andere Typen am selben Namen aus. |
| MX auf einen Alias | formal geladen, aber falsch | Der Server lädt die Zone mit Warnung; ein MX-Ziel darf kein CNAME sein. |

3. Die zweite Antwort enthält den CNAME und zusätzlich den A-Eintrag des Ziels, weil der Server den Alias selbst auflöst, wenn er für das Ziel zuständig ist.

### Teil 2

Forward/Reverse: Mismatch führt zu fehlerhaften Plausibilitätsprüfungen (zum Beispiel lehnen Mailserver Verbindungen ab, wenn die Rückrichtung nicht zum gemeldeten Namen passt) und zu unlesbaren Protokollen (nur Adressen statt Namen).

### Teil 5

1. Leeres Namensfeld = Name der Zeile davor (hier der Zonenursprung `@`, also `branch.example.org.`). `pc01` heißt `pc01.lab.branch.example.org.`. `pc02.lab` heißt `pc02.lab.branch.example.org.`. Die TTL `300` steht nur beim TXT-Eintrag; alle anderen erben `$TTL 3600`.
2. Ergebnisse: a) nur mit `dig` erkennbar; b) und f) Zone wird nicht geladen; c), d) Warnung, Zone lädt; e) kein Fehler, aber veränderte Daten. Konsequenz: `named-checkzone` ist notwendig, aber nicht hinreichend; nach dem Laden immer die wichtigsten Einträge mit `dig` gegenprüfen (das Prüfskript tut das).
3. Unterschiede hängen von der Windows-Version ab, typisch sind Kopfkommentare und andere Einrückung.

### Antworten auf die Kontrollfragen

1. Am Zonenursprung stehen immer SOA und NS. Ein CNAME erklärt den Namen zum Alias eines anderen und lässt keine weiteren Daten am Namen zu (RFC 1034 Abschnitt 3.6.2, RFC 2181 Abschnitt 10.1). Beides zusammen ist nicht möglich.
2. Zuerst der kleinste Präferenzwert: `mail1` (10), bei einem Fehlschlag `mail2` (20). Bei gleichem Wert wählt der absendende Server in zufälliger Reihenfolge (Lastverteilung; Grundlage ist RFC 5321, der nicht im Quellenverzeichnis des Lehrplans steht).
3. `25.50.168.192.in-addr.arpa`. Nibble-Format: Die Adresse auf 32 Hexziffern ausschreiben, die Ziffern umkehren, mit Punkten trennen und `ip6.arpa` anhängen (zum Beispiel `fd00:50::10` → `0.1.0.0…5.0.0.0.0.d.f.ip6.arpa`).
4. Der Name wird relativ gelesen und um den Zonennamen verlängert: Das Ziel lautet `web.branch.example.org.branch.example.org.`. Es existiert nicht; die Abfrage von `www.branch.example.org A` endet mit `NXDOMAIN`. `named-checkzone` meldet nichts.
5. Weil die Datei syntaktisch gültig ist und für ein CNAME-Ziel keine Prüfung auf Existenz erfolgt.
6. Priorität: kleinere Zahl wird zuerst versucht. Gewichtung: Verteilung der Last zwischen Zielen gleicher Priorität, proportional zum Gewicht (RFC 2782).
