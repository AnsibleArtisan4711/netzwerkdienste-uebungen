## Lernziele

Nach dieser Übung kannst du

- erklären, warum DHCP-Broadcasts Router nicht passieren, und die Arbeitsweise eines Relay-Agents (`giaddr`, Option 82) beschreiben,
- einen Relay-Agent unter Linux konfigurieren und die Funktion im Mitschnitt auf beiden Seiten nachweisen,
- für mehrere Subnetze Scopes planen, anlegen und dem Netz anhand der Relay-Adresse zuordnen,
- Superscopes und Multinetting erklären und vom Normalfall abgrenzen.

## Voraussetzungen

- Module 2 bis 4. Checkpoint `M5-Anfang` auf `SRV-WIN-DHCP1`, `RTR-LIN` und `CLI-WIN-A` (Teil 1).
- `RTR-LIN`: Pakete `isc-dhcp-relay` und `tcpdump` installiert (Modul 1), Schnittstellen `net-a`, `net-b`, `net-c`.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Relay-Agent** | Dienst auf einem Router, der Client-Broadcasts als Unicast an Server weiterleitet (RFC 1542). |
| **`giaddr`** | „Gateway IP Address“: Feld in der DHCP-Nachricht, das der Relay mit **seiner** Adresse im Client-Netz füllt. Der Server wählt danach den Scope. |
| **Hops** | Zähler der Relay-Stationen. |
| **Option 82** | Relay Agent Information (RFC 3046): Zusatzinformationen des Relays (z. B. Port, Kennung), meist von Switches ergänzt. |
| **Superscope** | Gruppe mehrerer Scopes, die auf demselben physischen Segment liegen. |
| **Multinetting** | Mehrere logische Subnetze auf einem Segment. |

*(Lerneinheit 5.1, Praxisaufgabe 1)*

```bash
sudo ./01.1-mitschnitt.sh net-b      # Client-Seite
sudo ./01.1-mitschnitt.sh net-a      # Server-Seite
```

**3. Lease anfordern** (`CLI-WIN-A`)

```powershell

ipconfig /renew
ipconfig /all
```

Erwartet: `CLI-WIN-A` bekommt keine Adresse (Link-Local, Modul 1). Im Mitschnitt auf `net-b` erscheinen DISCOVER-Pakete; auf `net-a` erscheinen **keine**. Notiere, warum: Der Router (`RTR-LIN`) leitet Broadcasts nicht weiter (auch nicht mit `ip_forward = 1`, das gilt nur für Unicast).

*(Lerneinheit 5.4, Praxisaufgabe 2)*

Planung:

| Eigenschaft | Wert |
|---|---|
| Name | `Netz-B` |

```powershell
Add-DhcpServerv4Scope -Name 'Netz-B' -StartRange 192.168.20.100 -EndRange 192.168.20.199 `

    -DnsServer 192.168.10.10 -DnsDomain corp.example.com
Get-DhcpServerv4Scope
```

Oder `.\05.1-scope-netz-b-anlegen.ps1 -WhatIf`, dann ohne `-WhatIf`. Der Server hat eine Schnittstelle nur in Netz A (`192.168.10.11`). Er ordnet eine Anfrage über `giaddr` einem Scope zu.

### Teil 3: Relay konfigurieren und nachweisen

*(Lerneinheiten 5.1, 5.3, Praxisaufgabe 3)*

**1. Relay konfigurieren** (`RTR-LIN`)

Die Debian-/Ubuntu-Pakete lesen `/etc/default/isc-dhcp-relay`; der Dienst `isc-dhcp-relay.service` baut daraus die Kommandozeile `dhcrelay -d -4 $OPTIONS -i … $SERVERS` (so in der Dienstdatei des Pakets, Ubuntu 24.04, geprüft). Die Datei kennt die Variablen `SERVERS`, `INTERFACES` und `OPTIONS`:

```bash
sudo cp 05.1-isc-dhcp-relay.default /etc/default/isc-dhcp-relay
cat /etc/default/isc-dhcp-relay
```

Inhalt der Beispieldatei:

```text
SERVERS="192.168.10.11"
INTERFACES="net-a net-b net-c"
OPTIONS=""
```

`INTERFACES` müssen **alle** Schnittstellen enthalten, auf denen Clients senden *und* über die Antworten vom Server kommen, also auch `net-a` (die Serverseite). `dhcrelay` fragt sonst nur die genannten Schnittstellen ab.

```bash
sudo systemctl restart isc-dhcp-relay
systemctl status isc-dhcp-relay --no-pager
```

Erwartet: `active (running)`. Bei Fehlern `journalctl -u isc-dhcp-relay -n 30`. Zum Ausprobieren ohne Dienst: `sudo dhcrelay -4 -d -i net-a -i net-b -i net-c 192.168.10.11` (Vordergrund, Strg+C beendet).

**2. Mitschnitte auf beiden Seiten** (`RTR-LIN`, zwei Sitzungen wie in Teil 1)

**3. Lease holen und prüfen** (`CLI-WIN-A`)

```powershell
ipconfig /release
ipconfig /renew
ipconfig /all
```

Erwartet: Adresse aus `192.168.20.100–199`, Router `192.168.20.1`. Auf dem Server:

```powershell
Get-DhcpServerv4Lease -ScopeId 192.168.20.0
```

**4. Mitschnitt lesen**

Ein gelesener Relay-Ablauf (Linux-Testlauf, Kea als Server, Netz C) steht in [`beispiele/05-relay-mitschnitt.md`](beispiele/05-relay-mitschnitt.md). Beantworte für deinen Mitschnitt:

| Frage | Client-Seite (`net-b`) | Server-Seite (`net-a`) |
|---|---|---|
| Quell-IP und Ziel-IP des DISCOVER | `0.0.0.0` → `255.255.255.255` | `192.168.10.1` → `192.168.10.11` |
| Wert im Feld `Gateway-IP` (`giaddr`) | – (leer) | `192.168.20.1` |
| Wert im Feld `hops` | 0 | 1 |
| Ziel-Port | 67 | 67 (Unicast, Quellport ebenfalls 67) |
| Quell-/Ziel-IP des OFFER | `192.168.20.1` → Client | `192.168.10.11` → `192.168.20.1` |

Die Werte der rechten Spalte hat der Testlauf so geliefert (Relay-Quelladresse: die Adresse der Schnittstelle zum Server). Der Server wählt den Scope anhand von `giaddr`, **nicht** anhand der Quelladresse.

> [!NOTE]
> Die Reservierung aus Modul 3 gilt nur in Netz A. Sie bleibt für `CLI-WIN-A` in Netz B ohne Wirkung: Die Reservierung hängt am Scope `192.168.10.0`. Notiere das: Wer einen Client zwischen Netzen verschiebt, braucht in jedem Scope eine eigene Reservierung.

**5. Checkliste für Fehlersuche am Relay** (ohne Umsetzung)

Typische Fehler (Lerneinheit 5.5): falscher Schnittstellenname in `INTERFACES`, Server-Seite fehlt, fehlende Route vom Server zur `giaddr`-Adresse (der Server antwortet an `giaddr`; ohne Route dorthin kommt nichts zurück), fehlender Scope für das Relay-Netz. Das letzte Szenario baust du in Modul 12 als Störung.

## Hintergrund

### Warum der Broadcast nicht ankommt

Ein Client ohne Adresse sendet DISCOVER an `255.255.255.255`. Router leiten diese Broadcasts nicht weiter. Damit ein Server in einem anderen Netz erreichbar wird, nimmt ein Relay den Broadcast an, trägt seine Adresse im Client-Netz in `giaddr` ein und schickt die Nachricht als Unicast an den Server. Der Server sucht den Scope, in dem `giaddr` liegt, und schickt die Antwort als Unicast an das Relay, das sie im Client-Netz weitergibt.

### Option 82

Mit der Relay Agent Information Option kann ein Relay (oder ein Switch) zusätzliche Informationen anhängen, etwa den Switch-Port. Der Server kann sie auswerten (z. B. per Policy, Modul 4) und muss sie in der Antwort unverändert zurückgeben. `dhcrelay` kann die Option mit `-a` anhängen (Hilfetext der Version 4.4.3); in diesem Kurs wird sie nicht benutzt.

### Superscope und Multinetting

Hängen mehr Clients an einem Segment, als ein Subnetz fasst, kann man das Segment mehrere logische Subnetze tragen lassen (Multinetting). Ein Superscope fasst die zugehörigen Scopes zusammen. Heute weicht man meist auf ein größeres Subnetz oder getrennte VLANs aus.

## Hinweise

- Die Schnittstellennamen stammen aus Modul 1 (`net-a`, `net-b`, `net-c`). Prüfe sie mit `ip -br link`.
- `tcpdump` meldet bei vom Relay gesendeten Paketen auf virtuellen Adaptern manchmal `bad udp cksum`; das ist ein Mitschnitt-Artefakt (Checksum-Offload), im Testlauf beobachtet.
- Mehrere Server hinter einem Relay: Das Relay schickt jede Anfrage an **alle** genannten Server (siehe Modul 7 und 8).

### Antworten auf die Kontrollfragen

1. `giaddr` trägt die Adresse des Relays im Client-Netz. Der Server sucht den Scope, in dem diese Adresse liegt, und vergibt daraus. Die Antwort geht an `giaddr`.
2. Alle Schnittstellen, auf denen Clients sitzen (net-b, net-c; auch net-a, wenn dort Clients sind), und die Schnittstelle zum Server (net-a). Antworten des Servers kommen dort an und müssen an das Client-Netz weitergegeben werden.
3. Kein Scope, keine Antwort: Der Client erhält nichts (Link-Local). Der Linux-Testlauf mit Kea ergab für diesen Fall: Kea verwirft das DISCOVER und protokolliert `failed to select a subnet`; es sendet kein NAK. Windows verhält sich *nicht bestätigt* ebenso; prüfe es in Modul 12.
4. Zusatzinformationen (z. B. Schalterport, Kennung) für die Zuordnung und Protokollierung. Sie werden von Relay oder Switch eingefügt.
5. Bei mehreren Subnetzen auf einem Segment. Heute löst man das meist mit einem größeren Subnetz oder VLANs.
