> [!WARNING]
> **Stand der Prüfung: Linux-Teil getestet, Windows-Teil nicht.** Konfiguration, Prüfung mit `kea-dhcp4 -t`, DORA über Relay, Reservierung und die Fehlermeldungen wurden in einer Testumgebung mit Ubuntu 24.04 und **Kea 2.4.1** (Paket aus den Ubuntu-Quellen) real ausgeführt (Netzwerk-Namespaces statt Hyper-V). **Nicht** getestet: Start über `systemctl` (in der Testumgebung nicht möglich), Verhalten mit echten Hyper-V-Switches und das Windows-Verhalten bei fehlendem Scope. Die Netzwerkkarte heißt im Test `sa`, hier `eth0`; passe sie an deinen Befund (`ip -br link`) an.

## Lernziele

Nach dieser Übung kannst du

- Kea DHCPv4 installieren, konfigurieren, prüfen und als Dienst betreiben,
- Subnetz, Pool, Optionen und Lease-Zeiten in der JSON-Konfiguration beschreiben,
- eine Reservierung per MAC-Adresse anlegen,
- den Server hinter dem Relay betreiben und den Ablauf im Mitschnitt und im Log nachvollziehen,
- typische Fehler (falsche Schnittstelle, fehlendes Subnetz, Dateirechte) erkennen.

## Voraussetzungen

- `RTR-LIN` mit Relay aus Modul 5.
- Neue VM `SRV-LIN-KEA`: Ubuntu Server 24.04, 1 vCPU, 1 GB RAM, `vSwitch-Server`, Adresse `192.168.10.21/24`, Gateway `192.168.10.1`, DNS `192.168.10.10`. Checkpoint `M8-Anfang` auf `RTR-LIN`.
- Internetzugang für `apt` (Hyper-V-Standardswitch mit NAT oder zeitweise externer Switch). Ohne Internet: Paketdateien vorab auf dem Hyper-V-Host herunterladen und kopieren; Vorgehen *nicht bestätigt*.
- `CLI-LIN-B` im Netz C (`vSwitch-ClientB`), DHCP-Client `dhclient` oder `networkctl`/`systemd-networkd` (Netzplan-Client).

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Kea** | DHCP-Server des ISC als Nachfolger des `isc-dhcp-server`; Konfiguration in JSON. |
| **`kea-dhcp4`** | Der DHCPv4-Dienst (Paket `kea-dhcp4-server`). |
| **memfile** | Lease-Datenbank als CSV-Datei, im Speicher gehalten. |
| **Pool** | Adressbereich eines Subnetzes, der dynamisch vergeben wird. |
| **Reservierung** | Feste Zuordnung MAC → Adresse in der Subnetz-Konfiguration. |
| **`kea-dhcp4 -t`** | Prüft eine Konfigurationsdatei, ohne den Dienst zu starten. |

## Testumgebung

| Gerät | Rolle | Adresse |
|---|---|---|
| `SRV-LIN-KEA` | Kea DHCPv4 | `192.168.10.21` (Netz A, `vSwitch-Server`) |
| `RTR-LIN` | Relay für Netz C | `.1` in jedem Netz |
| `CLI-LIN-B` | Client | Netz C, `192.168.30.0/24` |

Dateien: `08.1-kea-dhcp4.conf` (Grundkonfiguration), `08.1-kea-dhcp4-reservierung.conf` (mit Reservierung), `08.1-relay-auf-kea.default` (Relay-Konfiguration), `08.1-kea-pruefen.sh` (Prüfskript).

## Aufgabe

### Teil 1: Installation

*(Lerneinheit 8.1, Praxisaufgabe 1)*

```bash
sudo apt update
sudo apt install kea-dhcp4-server
kea-dhcp4 -V
```

Erwartet im Test: Version `2.4.1`. Dein Ergebnis kann abweichen, notiere die Version. Pfade: Konfiguration `/etc/kea/kea-dhcp4.conf`, Dienst `kea-dhcp4-server`, Benutzer `_kea`. Das Paket legt bereits eine Beispielkonfiguration an; sichere sie, bevor du sie ersetzt:

```bash
sudo cp /etc/kea/kea-dhcp4.conf /etc/kea/kea-dhcp4.conf.orig
```

### Teil 2: Konfiguration schreiben und prüfen

*(Lerneinheit 8.2, Praxisaufgabe 2)*

1. Schnittstellennamen ermitteln: `ip -br link`. Falls nicht `eth0`, in der Datei anpassen.
2. `08.1-kea-dhcp4.conf` nach `/etc/kea/kea-dhcp4.conf` kopieren (Rechte siehe unten).
3. **Vor dem Start prüfen:**

```bash
sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf; echo "Ausgang: $?"
```

Erwartet: Ausgang `0` und eine Meldung `DHCP4_CONFIG_COMPLETE`... (im Test mit `-t`: Meldungen bis `listening on interface`).

4. Dienst starten:

```bash
sudo systemctl enable --now kea-dhcp4-server
sudo systemctl status kea-dhcp4-server
```

Der Start per `systemctl` wurde in der Testumgebung **nicht** ausgeführt; der Prozess selbst lief dort mit der gleichen Datei.

5. Aufbau der Datei erklären (schriftlich, 5 Sätze): `interfaces-config`, `lease-database`, `valid-lifetime`/`renew-timer`/`rebind-timer`, `subnet4` mit `pools` und `option-data`, `loggers`.

**Dateirechte:** Der Dienst läuft als `_kea`. Gehört die Datei `root:root` mit Rechten `600`, kann er sie nicht lesen. Geeignet ist `root:_kea` mit `640`:

```bash
sudo chown root:_kea /etc/kea/kea-dhcp4.conf
sudo chmod 640 /etc/kea/kea-dhcp4.conf
```

### Teil 3: Relay auf Kea umstellen

*(Lerneinheit 8.3, Praxisaufgabe 3)*

Auf `RTR-LIN` in `/etc/default/isc-dhcp-relay`:

```bash
SERVERS="192.168.10.21"
```

Die ganze Datei steht in `08.1-relay-auf-kea.default`. Dann `sudo systemctl restart isc-dhcp-relay`. Der Relay trägt in jede weitergeleitete Anfrage die Adresse der Eingangsschnittstelle als Gateway ein (`giaddr`); Kea wählt daran das Subnetz.

Soll der Windows-Server weiter für Netz A und B arbeiten, trage beide Server ein (`SERVERS="192.168.10.11 192.168.10.21"`). Der Relay leitet dann jede Anfrage an beide; im Test mit zwei Servern antwortete nur der mit passendem Subnetz. Windows ohne Scope für Netz C: *nicht bestätigt*.

### Teil 4: Test und Nachweis

*(Lerneinheit 8.4, Praxisaufgabe 4)*

1. Mitschnitt auf `RTR-LIN` (Seite Netz C): `sudo ./01.1-mitschnitt.sh net-c`.
2. Auf `CLI-LIN-B` Adresse anfordern:

```bash
sudo dhclient -v net-c    # oder Netplan/networkd-Client
```

Im Test: `DHCPDISCOVER` → `DHCPOFFER of 192.168.30.100 from 192.168.30.1` → `DHCPREQUEST` → `DHCPACK`, danach `bound to 192.168.30.100`. Beachte, dass der Client den **Relay** (`192.168.30.1`) als Absender sieht.

3. Auf dem Server das Log lesen: `sudo journalctl -u kea-dhcp4-server -n 30`. Im Test erscheinen:

```text
DHCP4_LEASE_ADVERT [hwtype=1 d6:8a:0f:27:69:76], cid=[no info], tid=0x34552042: lease 192.168.30.100 will be advertised
DHCP4_LEASE_ALLOC  [hwtype=1 d6:8a:0f:27:69:76], cid=[no info], tid=0x34552042: lease 192.168.30.100 has been allocated for 28800 seconds
```

4. Lease-Datei ansehen: `sudo cat /var/lib/kea/kea-leases4.csv`. Im Test eine Zeile je Lease mit Adresse, MAC, Lease-Dauer, Ablaufzeit (Unix-Zeit), Subnetz-ID, Hostname.
5. Unix-Zeit lesbar machen: `date -d @<Ablaufzeit>`.

### Teil 5: Reservierung

*(Lerneinheit 8.5, Praxisaufgabe 5)*

1. MAC von `CLI-LIN-B` ermitteln: `ip -br link` (auf dem Client).
2. In der Datei `08.1-kea-dhcp4-reservierung.conf` den Platzhalter `aa:bb:cc:dd:ee:01` durch die echte MAC ersetzen und die Datei nach `/etc/kea/kea-dhcp4.conf` kopieren.
3. Prüfen (`kea-dhcp4 -t`) und Dienst neu starten: `sudo systemctl restart kea-dhcp4-server`.
4. Client: Lease freigeben (`sudo dhclient -r net-c`) und neu anfordern. Erwartet (Test): `192.168.30.50` statt `.100`; Log: `lease 192.168.30.50 will be advertised`, Hostname `cli-lin-b` in der CSV.

Die Reservierungsadresse liegt hier **außerhalb** des Pools (`.100–.199`). Eine Reservierung innerhalb des Pools wäre möglich; zur Wirkung auf die Poolvergabe bei Kea gibt es hier keinen Test: *nicht bestätigt*.

### Teil 6: Fehler provozieren

*(Lerneinheit 8.6, Praxisaufgabe 6)*

| Versuch | Wie | Erwartung im Test |
|---|---|---|
| Schnittstelle existiert nicht | `eth0` → `eth9` | `kea-dhcp4 -t` meldet: `Failed to select interface: interface 'eth9' doesn't exist in the system`, Ausgang ungleich 0 |
| Kein passendes Subnetz | Client in einem Netz ohne `subnet4` | Keine Antwort; Log: `DHCP4_PACKET_NAK_0001 … failed to select a subnet for incoming packet, src 192.168.10.1, type DHCPDISCOVER` |
| Datei nicht lesbar | `chmod 600`, Eigentümer `root:root` | Dienst startet nicht (Dienst läuft als `_kea`) |

Beachte: Das Fehlen eines Subnetzes führt bei Kea zu **Schweigen**, nicht zu einer NAK-Antwort an den Client, obwohl die Meldung `PACKET_NAK` heißt. Der Client sendet seine DISCOVER-Pakete mehrfach (im Test drei in zehn Sekunden) und gibt auf.

## Hintergrund

### Kea statt isc-dhcp-server

Der klassische `isc-dhcp-server` ist beendet. Kea nutzt JSON, arbeitet mit mehreren Threads und kennt Zusatzmodule (Hooks) und Datenbanken (MySQL, PostgreSQL) zusätzlich zum memfile. Für kleine Umgebungen reicht memfile.

### Das Subnetz als Schlüssel

Kea ordnet ein Paket einem Subnetz zu: Bei direkter Anfrage über die Schnittstelle, bei Relay-Paketen über `giaddr`. Ein Subnetz, das der Relay nicht kennt, wird nie gewählt. Deshalb muss die Subnetz-Definition exakt zum Netz hinter dem Relay passen.

### Lease-Datei

Die CSV-Datei wird an das Ende angehängt; ältere Zeilen derselben Adresse werden vom Lease-File-Cleanup (`lfc-interval`) zusammengefasst. Mehrere Zeilen zur selben Adresse sind deshalb kein Fehler; die letzte gilt.

### Eine Reservierung ohne feste Pool-Regel

Eine Reservierung bindet MAC und Adresse; der Client bekommt sie unabhängig von der Pool-Reihenfolge.

## Hinweise

- Nach jeder Änderung: erst `kea-dhcp4 -t`, dann Neustart. Ein fehlerhaftes JSON verhindert den Start.
- Das Protokoll (`stdout`/journald) genügt im Labor; eine Datei als Ziel braucht ein beschreibbares Verzeichnis für `_kea`.
- Keine Passwörter in der Kea-Konfiguration ablegen (Datenbanken sind hier nicht im Einsatz).

## Prüfbefehle und Kontrollfragen

```bash
kea-dhcp4 -V
sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf; echo $?
sudo systemctl status kea-dhcp4-server
sudo journalctl -u kea-dhcp4-server -n 30
sudo cat /var/lib/kea/kea-leases4.csv
```

Das Skript `08.1-kea-pruefen.sh` fasst die Prüfungen zusammen.

**Kontrollfragen**

1. Wozu dient `kea-dhcp4 -t`, und wann verwendest du es?
2. Wie wählt Kea das Subnetz für ein Paket, das über einen Relay kommt?
3. Was passiert, wenn kein passendes Subnetz existiert?
4. Warum ist `600 root:root` für die Konfigurationsdatei unter Ubuntu ein Problem?
5. Was bedeutet in der Lease-CSV das Feld `expire`, und wie machst du es lesbar?

## Erweiterungen

- Zweites Subnetz (Netz B) im selben Kea anlegen und mit dem Windows-Server vergleichen.
- Eigene Option, etwa `ntp-servers`, im Subnetz setzen und im Mitschnitt nachweisen.
- Lease-Zeit auf 10 Minuten stellen und das Renew-Verhalten beobachten (Mitschnitt, T1).

### Antworten

1. Prüft Syntax und Inhalt, ohne den Dienst zu starten oder zu stören; vor jedem Neustart.
2. Über `giaddr`, die Adresse der Relay-Schnittstelle; das Subnetz, zu dem sie passt, wird verwendet.
3. Kea verwirft das Paket, antwortet nicht; Hinweis nur im Log.
4. Der Dienst läuft als `_kea` und kann die Datei nicht lesen.
5. Zeitpunkt des Ablaufs als Unix-Zeit (Sekunden seit 1970); `date -d @<wert>`.

## Aufräumen und Rückkehr zum Ausgangszustand

- Reservierung aus der Konfiguration nehmen oder zur Grundkonfiguration zurückkehren, Dienst neu starten.
- Relay wieder auf `SERVERS="192.168.10.11"` stellen, wenn Netz C wieder entfällt.
- Checkpoint `M8-Ende` anlegen.
