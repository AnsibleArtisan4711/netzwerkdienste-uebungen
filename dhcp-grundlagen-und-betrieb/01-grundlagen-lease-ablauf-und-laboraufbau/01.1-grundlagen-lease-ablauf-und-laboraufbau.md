## Lernziele

Nach dieser Übung kannst du

- erklären, warum DHCP statt statischer Adressen eingesetzt wird, und welche Parameter DHCP vergibt,
- die Nachrichten DISCOVER, OFFER, REQUEST und ACK (DORA) sowie NAK, DECLINE, RELEASE und INFORM zuordnen und die Ports 67 und 68 erklären,
- T1 und T2 aus einer Lease-Dauer berechnen und das Verhalten ohne DHCP-Server (Link-Local-Adresse) erklären,
- die virtuellen Switches und den Linux-Router des Labors aufbauen,
- einen DHCP-Mitschnitt mit `tcpdump` lesen und Felder den Optionen zuordnen.

## Voraussetzungen

- Hyper-V-Host mit Rechten zum Anlegen von Switches und VMs.
- Installationsmedien für Debian 12 oder Ubuntu Server 24.04 sowie Windows 11 Enterprise (Evaluationsversion). Laufzeit der Evaluationsversionen vor Beginn prüfen.
- Internetzugang **nur** in der Vorbereitungsphase (Teil 1, Schritt 3).

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Lease** | Zeitlich begrenzte Vergabe einer Adresse samt Parametern. |
| **DORA** | Discover, Offer, Request, Acknowledge: der Standardablauf. |
| **BOOTP** | Vorgänger von DHCP (RFC 951, RFC 1542); DHCP verwendet dasselbe Paketformat. |
| **Option** | Eintrag aus Code, Länge und Wert in der DHCP-Nachricht (RFC 2132), z. B. Option 3 (Router). |
| **T1 / T2** | Zeitpunkt der Erneuerung (Standard 50 % der Lease-Dauer) und der erneuten Bindung (Standard 87,5 %). |
| **Link-Local-Adresse** | Adresse aus `169.254.0.0/16`, die sich ein Client selbst gibt, wenn kein Server antwortet (RFC 3927). |
| **Transaktions-ID (xid)** | Zufallszahl, mit der Client und Server zusammengehörige Nachrichten erkennen. |

## Aufgabe

### Teil 1: Labor aufbauen

*(Lerneinheit 1.1, Praxisaufgabe 1)*

**1. Switches anlegen** (Hyper-V-Host, PowerShell als Administrator)

```powershell
New-VMSwitch -Name vSwitch-Server  -SwitchType Private
New-VMSwitch -Name vSwitch-ClientA -SwitchType Private
New-VMSwitch -Name vSwitch-ClientB -SwitchType Private
Get-VMSwitch | Where-Object Name -like 'vSwitch-*' | Select-Object Name, SwitchType
```

Oder `.\01.1-switches-anlegen.ps1 -WhatIf`, dann ohne `-WhatIf`. Erwartet: drei Switches vom Typ `Private`. *GUI:* Hyper-V-Manager → *Virtual Switch Manager* → *Neuer virtueller Netzwerkswitch* → *Privat*.

**2. VM `RTR-LIN` anlegen**

1 vCPU, 1 GB RAM, 10 GB Festplatte, Debian 12 oder Ubuntu Server 24.04 ohne grafische Oberfläche. Der VM drei Netzwerkadapter geben:

```powershell
Connect-VMNetworkAdapter -VMName RTR-LIN -SwitchName vSwitch-Server    # erster Adapter
Add-VMNetworkAdapter     -VMName RTR-LIN -SwitchName vSwitch-ClientA
Add-VMNetworkAdapter     -VMName RTR-LIN -SwitchName vSwitch-ClientB
Get-VMNetworkAdapter -VMName RTR-LIN | Select-Object Name, SwitchName, MacAddress
```

Notiere die drei MAC-Adressen. Hat die VM Generation 2 und startet das Linux-Medium nicht, ist meist der Secure-Boot-Vorlagentyp falsch (*nicht bestätigt*; Hyper-V bietet dafür eine Vorlage für Linux-Medien).

**3. Pakete installieren (Internetphase)**

Hänge `RTR-LIN` vorübergehend zusätzlich an einen externen Switch mit Internetzugang. Dann:

```bash
sudo apt update
sudo apt install tcpdump
```

Für spätere Module werden die Pakete `isc-dhcp-relay` (ab Modul 5) und `radvd` (ab Modul 9) gebraucht. Installiere sie jetzt mit; Paketnamen und Verfügbarkeit hängen von der Distribution ab (unter Ubuntu 24.04 liegen beide im Archiv, getestet; Debian 12 *nicht bestätigt*). Die Installation startet `isc-dhcp-relay` eventuell mit leerer Konfiguration; das ist für diese Übung unerheblich.

> [!IMPORTANT]
> Danach den externen Adapter **entfernen** (`Remove-VMNetworkAdapter` bzw. Hyper-V-Manager) und die Linux-VMs für spätere Module (`SRV-LIN-KEA`, `CLI-LIN-B`) jetzt ebenfalls mit allen Paketen versorgen. Im Labor gibt es danach kein Internet mehr.

**4. Netzwerk von `RTR-LIN` konfigurieren**

Ersetze in `01.1-rtr-lin-netplan.yaml` die drei MAC-Adressen durch deine Werte (Ubuntu verwendet Netplan; Debian 12 verwendet standardmäßig `/etc/network/interfaces`, dann Adressen dort eintragen, *nicht bestätigt* für diese Übung). Die Datei benennt die Adapter über ihre MAC-Adresse in `net-a`, `net-b` und `net-c` um, damit die Namen in allen Modulen gleich sind.

```bash
sudo cp 01.1-rtr-lin-netplan.yaml /etc/netplan/60-labor.yaml
sudo chmod 600 /etc/netplan/60-labor.yaml
sudo netplan apply
ip -br addr
```

Erwartet: drei Schnittstellen `net-a`, `net-b`, `net-c` mit den Adressen `192.168.10.1/24`, `192.168.20.1/24`, `192.168.30.1/24`. Bei Fehlern `sudo netplan try`.

**5. Weiterleitung aktivieren**

```bash
sudo cp 01.1-rtr-lin-sysctl.conf /etc/sysctl.d/99-labor-forward.conf
sudo sysctl --system
cat /proc/sys/net/ipv4/ip_forward
```

Erwartet: `1`. Die Datei enthält `net.ipv4.ip_forward=1`.

**6. Abschluss**

Prüfe, dass `RTR-LIN` keinen Adapter außerhalb der drei privaten Switches hat (`Get-VMNetworkAdapter -VMName RTR-LIN | Select-Object SwitchName`). Erstelle den Checkpoint `BASIS`:

```powershell
Checkpoint-VM -Name RTR-LIN -SnapshotName BASIS
```

Hänge `CLI-WIN-A` an `vSwitch-Server` (`Connect-VMNetworkAdapter -VMName CLI-WIN-A -SwitchName vSwitch-Server`).

### Teil 2: Verhalten ohne DHCP-Server

*(Lerneinheit 1.3, Praxisaufgabe 2)*

Es gibt noch keinen DHCP-Server im Labor. Was macht ein Client?

**1. Mitschnitt starten** (`RTR-LIN`, in einer zweiten Sitzung)

```bash
sudo tcpdump -n -e -vv -i net-a 'udp port 67 or udp port 68'
```

Die Datei `01.1-mitschnitt.sh` kapselt das (`./01.1-mitschnitt.sh net-a`). Der Ausdruck `udp port 67 or udp port 68` entspricht dem Filter `port 67 or port 68` des Lehrplans, schränkt aber auf UDP ein.

**2. Client auf automatische Adresse stellen** (`CLI-WIN-A`)

- **GUI:** *Einstellungen* → *Netzwerk und Internet* → *Ethernet* → *IP-Zuweisung* → *Bearbeiten* → *Automatisch (DHCP)*.
- **PowerShell (als Administrator):**

```powershell
Set-NetIPInterface -InterfaceAlias 'Ethernet' -Dhcp Enabled
ipconfig /renew
ipconfig /all
```

Der Name `Ethernet` kann abweichen (`Get-NetAdapter`).

**3. Beobachten und notieren**

- Welche Adresse hat der Client nach einigen Minuten? Erwartet (*nicht bestätigt* für die konkrete Windows-Version): eine Adresse aus `169.254.0.0/16` (Eintrag zur Autokonfiguration in `ipconfig /all`).
- Wie viele DISCOVER-Pakete erscheinen, in welchen Abständen? Notiere die Zeitstempel der ersten fünf Pakete. Der Rhythmus hängt vom Client ab; ein allgemeingültiger Wert wird hier nicht behauptet.
- Hinweis: Hat der Client eine Link-Local-Adresse, aber eine Anwendung meldet „kein Netzwerk“, ist die erste Frage in der Fehlersuche, ob ein DHCP-Server erreichbar ist (Modul 12).

### Teil 3: Eine DISCOVER-Nachricht lesen

*(Lerneinheit 1.2 und 1.4, Praxisaufgabe 3)*

Werte ein DISCOVER aus Teil 2 aus. Ein vollständiges Beispiel mit allen vier DORA-Nachrichten (aus dem Linux-Testlauf, nur die Netz-C-Seite) steht in [`beispiele/01-dora-mitschnitt.md`](beispiele/01-dora-mitschnitt.md). Fülle für dein DISCOVER die Tabelle aus:

| Feld im Mitschnitt | Dein Wert | Bedeutung / zugehörige Option |
|---|---|---|
| Quell-IP und Port | | Client hat noch keine Adresse: `0.0.0.0`, Port 68 |
| Ziel-IP und Port | | Broadcast `255.255.255.255`, Port 67 |
| Quell-MAC / Ziel-MAC | | Ziel-MAC `ff:ff:ff:ff:ff:ff` |
| Transaktions-ID `xid` | | gleich in DISCOVER, OFFER, REQUEST, ACK |
| `Client-Ethernet-Address` | | MAC des Clients (Feld `chaddr`); Option 61 (Client-Identifier) kann zusätzlich vorkommen |
| `DHCP-Message (53)` | | Nachrichtentyp: Discover |
| `Hostname (12)` | | vom Client gesendeter Name |
| `Parameter-Request (55)` | | Liste der Optionen, die der Client haben möchte (z. B. 1 Subnetzmaske, 3 Router, 6 DNS-Server, 15 Domänenname) |

Ordne jeder Angabe die Option aus Einheit 1.4 zu. Wie `tcpdump` die Felder darstellt, hängt von der Version ab (Beispiel: 4.99.4, *nicht bestätigt* für andere Versionen).

## Hintergrund

### Warum DHCP

Statische Adressen verursachen Doppelvergaben, Tippfehler und viel Handarbeit. DHCP vergibt Adresse, Subnetzmaske, Standardgateway und DNS-Server zentral, die Adressen kehren nach Ablauf der Lease in den Pool zurück. Als Format dient das Paket von BOOTP (RFC 951); RFC 1542 beschreibt die Weiterleitung über Router; DHCP selbst steht in RFC 2131, die Optionen in RFC 2132.

### Der Ablauf

1. **DISCOVER:** Der Client hat noch keine Adresse und ruft per Broadcast „Gibt es einen Server?“ (UDP 68 → 67).
2. **OFFER:** Ein Server bietet eine Adresse samt Optionen an.
3. **REQUEST:** Der Client nimmt ein Angebot an und nennt dabei den Server (Server-Identifier), damit andere Server ihr Angebot zurückziehen.
4. **ACK:** Der Server bestätigt; die Lease beginnt.

Weitere Nachrichten: **NAK** (Server lehnt ab, z. B. Adresse passt nicht zum Netz), **DECLINE** (Client lehnt ab, z. B. weil die Adresse schon belegt ist), **RELEASE** (Client gibt die Adresse zurück), **INFORM** (Client hat eine feste Adresse und fragt nur nach Optionen). Der erste Broadcast ist nötig, weil der Client weder die eigene noch die Adresse des Servers kennt. Die Ports sind 67 (Server) und 68 (Client).

### Lease-Lebenszyklus

Bei T1 (Standard 50 %) fragt der Client **seinen** Server per Unicast nach Verlängerung. Klappt das nicht, sendet er bei T2 (Standard 87,5 %) einen Broadcast an **jeden** Server. Läuft die Lease ab, muss der Client die Adresse aufgeben und von vorn beginnen. Findet ein Client keinen Server, vergibt er sich selbst eine Adresse aus `169.254.0.0/16` und prüft per ARP, dass sie frei ist (RFC 3927, RFC 5227). Solche Adressen sind im Labor ein sicheres Zeichen für „kein DHCP-Server erreichbar“.

## Hinweise

- Ein Mitschnitt auf `RTR-LIN` sieht nur Netz A, solange der Client dort hängt. Mitschnitte auf der Gegenseite brauchen eine eigene Sitzung (Modul 5).
- Auf virtuellen Adaptern meldet `tcpdump` manchmal `bad udp cksum`, obwohl die Pakete in Ordnung sind: Die Prüfsumme wird erst nach dem Mitschnitt berechnet (Checksum-Offload). Im Linux-Testlauf trat das bei vom Relay gesendeten Paketen auf; ob Hyper-V dasselbe zeigt, ist *nicht bestätigt*.
- Der Checkpoint `BASIS` auf `RTR-LIN` ist der Rücksprungpunkt für alle späteren Module.

### Antworten auf die Kontrollfragen

1. Server UDP 67, Client UDP 68. Der Client kennt weder eigene Adresse noch Server und kann nur an alle senden (Broadcast).
2. T1 nach 4 Stunden, T2 nach 7 Stunden.
3. Der Client konfiguriert sich nach RFC 3927 selbst. Für die Fehlersuche heißt das: Ein DHCP-Server ist nicht erreichbar oder antwortet nicht (Dienst, Netz, Relay, Scope; Modul 12).
4. Der Client nennt die Optionen, die er gern hätte; der Server sendet davon, was er konfiguriert hat.
5. NAK: der Server kann die gewünschte Adresse nicht bestätigen (z. B. Client ist in ein anderes Netz gewechselt oder die Adresse ist vergeben). DECLINE: der Client stellt fest, dass die angebotene Adresse schon benutzt wird (Konflikterkennung, RFC 5227).
