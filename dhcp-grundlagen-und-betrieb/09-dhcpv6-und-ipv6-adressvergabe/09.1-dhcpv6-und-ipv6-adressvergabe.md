## Lernziele

Nach dieser Übung kannst du

- SLAAC, zustandsloses und zustandsbehaftetes DHCPv6 unterscheiden und die RA-Flags M und O erklären,
- Router Advertisements mit `radvd` konfigurieren,
- einen DHCPv6-Server unter Windows und unter Kea einrichten,
- DHCPv6 mit DHCPv4 vergleichen (Nachrichten, DUID, IAID, Relay) und den Ablauf im Mitschnitt zuordnen.

## Voraussetzungen

- Lab-Netze aus Modul 1 bis 5, zusätzlich IPv6: `RTR-LIN` bekommt in jedem Netz `fd00:<n>::1/64` (Netz A `fd00:10::`, B `fd00:20::`, C `fd00:30::`), `net.ipv6.conf.all.forwarding=1`.
- Windows-Server `SRV-WIN-DHCP1` (Netz A, Adresse `fd00:10::11/64` zusätzlich), `SRV-LIN-KEA` (Adresse `fd00:10::21/64`).
- Checkpoint `M9-Anfang` auf `RTR-LIN`.

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **SLAAC** | Client bildet seine Adresse selbst aus dem Präfix des Routers (RA). |
| **RA** | Router Advertisement, enthält Präfix und die Flags M und O. |
| **M-Flag** | „Managed“: Adresse per DHCPv6 beziehen. |
| **O-Flag** | „Other“: übrige Optionen (DNS) per DHCPv6 beziehen. |
| **DUID / IAID** | Kennung des Clients bzw. der Schnittstelle (statt MAC beim DHCPv4). |
| **Solicit, Advertise, Request, Reply** | Nachrichten des DHCPv6-Ablaufs (statt DORA). |

## Aufgabe

### Teil 1: IPv6 im Labor vorbereiten

*(Lerneinheit 9.1)*

Auf `RTR-LIN` (Netplan-Datei aus Modul 1 um Adressen ergänzen, `netplan generate`, `netplan apply`) und Weiterleitung aktivieren:

```bash
sudo sysctl -w net.ipv6.conf.all.forwarding=1
sudo apt install radvd
```

Adressen: `net-a fd00:10::1/64`, `net-b fd00:20::1/64`, `net-c fd00:30::1/64`. Prüfe mit `ip -6 addr` und teste `ping fd00:10::11` aus Netz B.

### Teil 2: Router Advertisement

*(Lerneinheit 9.2, Praxisaufgabe 1)*

1. Konfiguration `09.1-radvd.conf` nach `/etc/radvd.conf` kopieren. Im Test wurde sie mit `radvd -c -C 09.1-radvd.conf` geprüft: *syntax ok*.
2. `sudo systemctl restart radvd`.
3. **Vergleich der Varianten.** Setze nacheinander und beobachte `CLI-LIN-B` bzw. `CLI-WIN-A` im Netz B:

| Variante | Einstellung | Erwartung (nicht bestätigt) |
|---|---|---|
| SLAAC | M off, O off, `AdvAutonomous on` | Client bildet Adresse selbst, kein DHCPv6 |
| Stateless DHCPv6 | M off, O on, `AdvAutonomous on` | Adresse per SLAAC, DNS per DHCPv6 |
| Stateful DHCPv6 | M on, O on, `AdvAutonomous off` | Adresse per DHCPv6 (Konfiguration der Übung) |

4. RA im Mitschnitt: `sudo tcpdump -ni net-b -vv icmp6 and ip6[40] == 134`. Suche die Flags (Ausgabeformat *nicht bestätigt*).

### Teil 3: DHCPv6 unter Windows

*(Lerneinheit 9.3, Praxisaufgabe 2)*

- **GUI:** `dhcpmgmt.msc` → IPv6 → Rechtsklick → *Neuer Bereich*, Präfix `fd00:20::`, Name `Netz-B-v6`, Lebenszeiten, aktivieren.
- **PowerShell:**

```powershell
Add-DhcpServerv6Scope -Prefix fd00:20:: -Name 'Netz-B-v6' -State Active `
    -PreferredLifetime (New-TimeSpan -Hours 3) -ValidLifeTime (New-TimeSpan -Hours 4) `
    -T1 (New-TimeSpan -Hours 1) -T2 (New-TimeSpan -Hours 2)
Set-DhcpServerv6OptionValue -Prefix fd00:20:: -DnsServer fd00:10::10 -DomainSearchList corp.example.com -Force
Get-DhcpServerv6Scope
```

Oder `.\09.1-dhcpv6-scope-netz-b.ps1 -WhatIf`, dann ohne `-WhatIf`. Hinweise aus der Dokumentation: `-ValidLifeTime` muss größer oder gleich `-PreferredLifetime` sein, `-T1` kleiner als `-T2`, `-T2` kleiner als `-PreferredLifetime`. `-Force` überspringt die Prüfung des DNS-Servers. Ob Windows für DHCPv6 Ausschlussbereiche und Reservierungen über `Add-DhcpServerv6ExclusionRange` / `Add-DhcpServerv6Reservation` genau so anlegt wie bei IPv4, ist *nicht bestätigt*.

### Teil 4: DHCPv6 mit Kea und Relay

*(Lerneinheit 9.4, Praxisaufgabe 3)*

1. Auf `SRV-LIN-KEA`: `sudo apt install kea-dhcp6-server`. Konfiguration `09.1-kea-dhcp6.conf` nach `/etc/kea/kea-dhcp6.conf` (Schnittstelle `eth0` anpassen), prüfen mit `sudo kea-dhcp6 -t /etc/kea/kea-dhcp6.conf` und starten: `sudo systemctl enable --now kea-dhcp6-server`.
2. Relay auf `RTR-LIN`: Datei `09.1-isc-dhcp-relay6.default` nach `/etc/default/isc-dhcp-relay6` (Dienst `isc-dhcp-relay6.service`). Die Schnittstellenaufteilung (`LOWER_INTERFACES`, `UPPER_INTERFACES`) und der Server-Eintrag müssen für dein Netz angepasst werden; Relay-Verhalten und Optionsnamen sind **nicht getestet**.
3. Client `CLI-LIN-B`: `sudo dhclient -6 -v net-c`. Erwartet: SOLICIT → ADVERTISE → REQUEST → REPLY, Adresse im Pool `fd00:30::100–fd00:30::1ff`.
4. Lease-Datei: `sudo cat /var/lib/kea/kea-leases6.csv` (Spalten u. a. `address`, `duid`, `valid_lifetime`, `pref_lifetime`, `iaid`).

**Hinweis zum Testlauf:** Beim Start in der Sandbox scheiterte Kea6 mit `unable to open DUID file /var/lib/kea/kea-dhcp6-serverid for writing`, weil das Verzeichnis dort nicht für den Testbenutzer beschreibbar war. Das ist Umgebungsbedingt; auf dem echten System gehört das Verzeichnis `_kea`.

### Teil 5: Vergleich und Mitschnitt

*(Lerneinheit 9.5, Praxisaufgabe 4)*

Beantworte schriftlich mit Hilfe des Mitschnitts (`tcpdump -ni net-b -vv port 546 or port 547`):

1. Welche Multicast-Adresse nutzt der Client für SOLICIT (erwartet: `ff02::1:2`, Port 547)?
2. Wodurch identifiziert der Server den Client (DUID statt MAC)?
3. Wie unterscheidet sich der Ablauf von DORA?
4. Wie erfährt ein Client den Standardrouter, wenn DHCPv6 keine Router-Option kennt?

## Hintergrund

### Wer sagt was?

IPv6 trennt Aufgaben: Der **Router** nennt per RA Präfix, Standardroute und Flags. DHCPv6 liefert nur Adressen und Optionen, **nie den Standardrouter**. Deshalb braucht jedes Netz mit DHCPv6 einen Router, der RAs sendet.

### SLAAC, stateless, stateful

Bei SLAAC bildet der Client die Adresse selbst. Beim zustandslosen DHCPv6 holt er nur DNS-Daten, der Server führt keine Leases. Beim zustandsbehafteten DHCPv6 verwaltet der Server Adressen wie bei DHCPv4, mit DUID und IAID statt MAC.

### Datenschutz

SLAAC-Adressen mit Privacy Extensions wechseln; dadurch lassen sich Geräte schwerer verfolgen, aber auch schlechter im Log zuordnen. Für Server-Adressierung bieten sich Reservierungen oder statische Adressen an.

### Relay

Im IPv6-Relay steckt die Nachricht des Clients in einer „Relay-Forward“-Nachricht; der Server antwortet an den Relay. Die Details (Relay-Message-Option) sind hier nicht getestet.

## Hinweise

- Wenn der Client keine DHCPv6-Antwort bekommt, prüfe zuerst RA und Flags, dann die Erreichbarkeit des Servers.
- Windows-Clients sprechen DHCPv6 nur bei gesetztem M- oder O-Flag; das Verhalten der Windows-11-Version im Labor ist *nicht bestätigt*.
- Das Lab nutzt ULA-Präfixe (`fd00::/8`); für echte Netze würde man ein zugewiesenes oder zufällig gewähltes ULA-Präfix verwenden.

## Musterlösung

<details>
<summary>Musterlösung anzeigen</summary>

### Soll-Zustand (zu erwarten, nicht bestätigt)

| Prüfung | Soll |
|---|---|
| RA | Präfix `fd00:20::/64`, M und O gesetzt, kein Autonomous |
| Client Netz B | Adresse aus `fd00:20::/64` per DHCPv6, DNS `fd00:10::10` |
| Client Netz C | Adresse aus `fd00:30::100–1ff` |
| Mitschnitt | SOLICIT an `ff02::1:2`, Port 547 |

### Antworten

1. M: Adresse per DHCPv6; O: sonstige Optionen per DHCPv6. Der Router setzt sie im RA.
2. Der Router ist über RA bekannt; DHCPv6 ist dafür nicht vorgesehen.
3. Über die DUID.
4. SOLICIT, ADVERTISE, REQUEST, REPLY ↔ DISCOVER, OFFER, REQUEST, ACK.
5. SLAAC genügt für einfache Netze ohne Nachvollziehbarkeit; DHCPv6 bei Bedarf an Zuordnung, Protokollierung und Optionen.

</details>
